# بازطراحی کامل Business Discovery — 1000 URL Batch + Sequential Crawl + External Boolean Approval

Repository:
https://github.com/ARVIN-B/business-discovery

ابتدا کل کد فعلی پروژه را بررسی کن، مخصوصاً فایل‌های زیر:

- `app/main.py`
- `app/job_manager.py`
- `app/job_store.py`
- `tests/test_discovery.py`
- `tests/test_jobs.py`
- `test_service.py`
- `README.md`

سپس منطق فعلی Search → URL Queue → Crawl → Result را با معماری زیر بازطراحی و واقعاً پیاده‌سازی کن.

**در این مرحله فقط Repository مربوط به `business-discovery` را تغییر بده. به `info_extractor` دست نزن.** هدف این است که Business Discovery آمادهٔ اتصال به Info شود.

## 1. منطق کلی جدید

اطلاعات جست‌وجو از سمت `info` دریافت می‌شود؛ شامل keyword، province و سایر پارامترهای موردنیاز.

Business Discovery باید این چرخه را اجرا کند:

1. از SearXNG تعداد ۱۰۰۰ URL یکتای واقعی و معتبر جمع‌آوری کند.
2. تمام این ۱۰۰۰ URL را در صف پایدار ذخیره کند.
3. پس از تکمیل جمع‌آوری batch، پردازش URLها را یکی‌یکی شروع کند.
4. هر URL را با Firecrawl پردازش کند.
5. پس از اتمام هر URL، تمام نتایج جدید همان URL را به `info` برگرداند.
6. منتظر تأیید `info` بماند.
7. اگر پاسخ `true` بود، URL بعدی را پردازش کند.
8. اگر پاسخ `false` بود، کل Job را متوقف کند و هیچ URL دیگری را پردازش نکند.
9. وقتی ۱۰۰۰ URL اول تمام شدند و آخرین تأیید `true` بود، batch بعدی ۱۰۰۰ URL را از SearXNG جمع‌آوری کند.
10. همین روند تا توقف توسط `info` یا اتمام واقعی فضای جست‌وجو ادامه داشته باشد.

**هیچ محدودیت ثابت ۳ round یا ۳ درخواست جست‌وجو نباید وجود داشته باشد.**

## 2. جمع‌آوری URLها از SearXNG

مهم‌ترین نکته این است که ابتدا batch کامل جمع‌آوری شود و بعد Crawl شروع شود.

یک تنظیم قابل تغییر ایجاد کن:

`SEARCH_BATCH_SIZE=1000`

رفتار مورد انتظار:

- تا زمانی که ۱۰۰۰ URL یکتای معتبر جمع نشده، هیچ URLی برای Crawl ارسال نشود.
- برای رسیدن به ۱۰۰۰ URL، SearXNG باید صفحه‌به‌صفحه درخواست دریافت کند.
- محدودیت فعلی `MAX_SEARCH_ROUNDS = 3` حذف شود.
- محدودیت پیش‌فرض ۵۰ صفحه نیز نباید باعث پایان اشتباه جست‌وجو شود.
- اگر یک query تمام صفحاتش را مصرف کرد ولی هنوز ۱۰۰۰ URL جمع نشده، query بعدی از Search Strategy اجرا شود.
- اگر SearXNG یک صفحهٔ خالی برگرداند، فقط همان query تمام‌شده محسوب شود؛ نه کل Job.
- پس از مصرف صفحات یک query، cursor و شمارهٔ صفحهٔ بعدی آن ذخیره شود.
- بعد از پردازش batch اول، برای batch دوم از cursor ذخیره‌شده ادامه بده؛ جست‌وجو را از صفحهٔ اول شروع نکن.
- اگر یک صفحه بیشتر از ظرفیت باقی‌ماندهٔ batch نتیجه داشت، URLهای اضافه را دور نریز؛ آن‌ها را برای batch بعدی ذخیره کن.

Search Strategy باید به‌صورت قابل توسعه طراحی شود. منطق فعلی `search_query_for_round` که عملاً فقط سه حالت دارد و بعد از آن queryهای تکراری تولید می‌کند، کافی نیست.

از ترکیب‌های متنوع و غیرتکراری keyword، province و عبارت‌های مرتبط با هدف جست‌وجو استفاده کن. وضعیت مصرف هر query و pagination آن باید مستقل و پایدار ذخیره شود.

## 3. جلوگیری قطعی از URL تکراری

Deduplication باید در کل طول عمر یک Job انجام شود، نه فقط URLهایی که Crawl شده‌اند.

برای این کار:

- هر URL قبل از ورود به صف normalize شود.
- تمام URLهای کشف‌شده، حتی آن‌هایی که هنوز Crawl نشده‌اند، در مجموعهٔ `seen_urls` ثبت شوند.
- URL تکراری در همان صفحه، صفحات بعدی، queryهای متفاوت یا batchهای بعدی نباید دوباره وارد صف شود.
- از منطق فعلی `normalize_url` استفاده و آن را در صورت نیاز کامل کن.
- URLهای متفاوت یک دامنه همچنان مستقل باقی بمانند؛ فقط URL یکسان حذف شود.
- `processed_urls` به‌تنهایی برای این هدف کافی نیست، چون URLهای pending را پوشش نمی‌دهد.

وضعیت صف، URLهای کشف‌شده، URLهای پردازش‌شده و cursor جست‌وجو باید در SQLite ذخیره شوند.

## 4. پردازش URLها به‌صورت کاملاً ترتیبی

در این معماری فقط یک URL در هر لحظه اجازهٔ Crawl دارد.

برای هر URL:

1. URL از صف برداشته شود.
2. وضعیت آن `processing` شود.
3. با Firecrawl پردازش شود.
4. تمام صفحات استخراج‌شده از آن URL بررسی شوند.
5. تمام شماره‌های موبایل معتبر normalize و با نتایج کل Job deduplicate شوند.
6. تمام نتایج جدید همان URL به‌صورت یک batch کامل ذخیره شوند.
7. رویداد تکمیل URL برای `info` ارسال شود.
8. سیستم وارد وضعیت `awaiting_approval` شود.
9. هیچ URL دیگری Crawl نشود تا پاسخ `info` دریافت شود.

در این حالت `MAX_CONCURRENT_SITES` نباید باعث پردازش هم‌زمان چند URL شود. برای این workflow، پردازش URLها strictly sequential باشد.

منطق فعلی که ممکن است چند URL را با `asyncio.as_completed` هم‌زمان پردازش کند، باید اصلاح شود.

نکته: یک URL ممکن است چند صفحهٔ واقعی و چند شمارهٔ موبایل داشته باشد. تمام نتایج آن URL باید کامل و یکجا برگردند؛ هیچ نتیجه‌ای را به خاطر تعداد یا محدودیت داخلی truncate نکن.

## 5. پروتکل تأیید ادامه از سمت Info

یک API مشخص برای دریافت تصمیم `info` پیاده‌سازی کن.

Endpoint پیشنهادی:

`POST /v1/jobs/{job_id}/decisions/{decision_id}`

Body باید دقیقاً یک JSON Boolean باشد:

برای ادامه:

```json
true
```

برای توقف:

```json
false
```

هیچ فیلد اضافه‌ای مانند `continue`, `approved` یا `status` در Body قرار نده. شناسهٔ تصمیم در URL قرار دارد و Body فقط `true` یا `false` است.

### رفتار تصمیم

**وقتی true دریافت شد:**

- تصمیم در SQLite ذخیره شود.
- سیستم از وضعیت `awaiting_approval` خارج شود.
- URL بعدی همان batch پردازش شود.
- اگر batch تمام شده، جمع‌آوری batch بعدی از SearXNG شروع شود.

**وقتی false دریافت شد:**

- درخواست توقف ثبت شود.
- هیچ URL دیگری Crawl نشود.
- هیچ batch جدیدی از SearXNG دریافت نشود.
- Job با وضعیت `stopped` تمام شود.
- نتایج قبلی حفظ شوند.

برای هر URL یک `decision_id` یکتا تولید کن. این شناسه باید در رویداد SSE همان URL قرار بگیرد تا پاسخ دیرهنگام یا تکراری مربوط به URL قبلی نتواند URL بعدی را ناخواسته آزاد کند.

تصمیم‌ها باید idempotent باشند:

- تکرار همان تصمیم برای همان `decision_id` مشکلی ایجاد نکند.
- تصمیم متناقض برای یک `decision_id` قبلاً تعیین‌شده با خطای مناسب رد شود.
- تصمیم مربوط به Job یا URL نامعتبر رد شود.
- فقط Boolean واقعی پذیرفته شود؛ مقادیر رشته‌ای `"true"` و `"false"` پذیرفته نشوند.

## 6. ارسال نتیجهٔ هر URL به Info

در حال حاضر `url_results_found` فقط در صورت پیدا شدن شمارهٔ جدید ارسال می‌شود. این رفتار برای workflow جدید کافی نیست.

یک رویداد پایدار جدید با نام زیر ایجاد کن:

`url_completed`

این رویداد باید بعد از تکمیل هر URL، حتی زمانی که هیچ شماره‌ای پیدا نشده، ارسال شود.

ساختار پیشنهادی:

```json
{
  "candidate_url": "https://example.ir/page",
  "results": [],
  "new_results_count": 0,
  "error": null,
  "decision_id": "unique-id",
  "decision_url": "/v1/jobs/JOB_ID/decisions/unique-id"
}
```

اگر موبایل پیدا شده باشد، آرایهٔ `results` شامل تمام شماره‌های جدید و اطلاعات واقعی آن‌ها باشد:

- number
- source_url
- website_url
- page_title
- page_description

اگر Crawl خطا داشت، همچنان `url_completed` ارسال شود و خطا در فیلد `error` قرار بگیرد. در این حالت نیز Business Discovery منتظر Boolean از `info` بماند.

رویداد فعلی `url_results_found` را برای سازگاری با مصرف‌کننده‌های قبلی حفظ کن، اما در workflow جدید، `info` باید برای دریافت نتیجهٔ کامل هر URL از `url_completed` استفاده کند تا نتیجهٔ یک URL دوبار شمرده نشود.

نتایج، وضعیت URL و رویداد مربوط به آن باید به‌شکل اتمیک در SQLite ثبت شوند.

## 7. پایداری و Recovery

این قسمت بسیار مهم است.

چون سیستم ممکن است هنگام دریافت ۱۰۰۰ URL، هنگام Crawl یا هنگام انتظار برای تأیید Info ری‌استارت شود، هیچ وضعیت مهمی نباید فقط در حافظه باشد.

موارد زیر باید در SQLite ذخیره شوند:

- URLهای batch فعلی و ترتیب آن‌ها
- URLهای کشف‌شده در کل Job
- URLهای پردازش‌شده
- batch فعلی
- cursor و شمارهٔ صفحهٔ هر query
- queryهای استفاده‌شده و queryهای باقی‌مانده
- وضعیت هر URL
- نتیجهٔ کامل هر URL
- `pending_decision_id`
- تصمیم ثبت‌شده برای هر URL
- وضعیت Job

اگر سرویس هنگام `awaiting_approval` ری‌استارت شد:

- همان Job باید Recovery شود.
- همان `decision_id` معتبر باقی بماند.
- سیستم باید همچنان منتظر پاسخ همان تصمیم باشد.
- بدون دریافت `true` نباید URL بعدی را Crawl کند.

اگر سرویس هنگام پردازش URL ری‌استارت شد، همان URL باید به‌شکل امن قابل ادامه یا پردازش مجدد باشد؛ بدون تکرار شماره‌ها و رویدادهای ثبت‌شده.

از `asyncio.Event` صرفاً به‌عنوان سیگنال بیدار کردن task استفاده کن؛ منبع حقیقت باید state ذخیره‌شده در دیتابیس باشد.

Endpoint فعلی `/stop` نیز باید همچنان کار کند و بتواند Job در حال انتظار برای تأیید را متوقف کند.

## 8. مدیریت پایان جست‌وجو و خطا

پایان یک query یا رسیدن به یک صفحهٔ خالی به معنی پایان کل Search نیست.

Job فقط در این شرایط می‌تواند `completed` شود:

- تمام queryهای برنامه‌ریزی‌شده و معتبر بررسی شده باشند.
- pagination مربوط به آن‌ها واقعاً exhausted شده باشد.
- URL جدید و یکتای دیگری باقی نمانده باشد.
- صف URLها خالی شده باشد.
- تصمیم معلقی وجود نداشته باشد.

خطای موقت SearXNG نباید به‌عنوان search exhaustion یا پایان موفق Job تلقی شود. cursor را حفظ کن و برای خطاهای موقت، retry پایدار با تأخیر قابل تنظیم (پیش‌فرض ۶۰ ثانیه) پیاده‌سازی کن. در صورت وجود `Retry-After` معتبر، آن را نیز رعایت کن.

خطای Firecrawl برای یک URL باید همراه همان URL به `info` گزارش شود. نباید باعث حذف نتایج قبلی یا توقف خودکار کل جست‌وجو شود.

**نکتهٔ اصلی:** Business Discovery در حالت اتصال به Info نباید خودش بر اساس تعداد موبایل‌های پیدا شده تصمیم بگیرد که جست‌وجو را تمام کند. مرجع تصمیم‌گیری برای ادامه فقط Boolean دریافت‌شده از Info است. فیلد `count` را برای سازگاری API نگه دار، اما در این workflow نباید باعث توقف خودکار شود.

## 10. تست‌های ضروری

تست‌ها را مطابق منطق جدید بازنویسی و تکمیل کن:

1. ثابت شود تا قبل از جمع‌آوری ۱۰۰۰ URL، هیچ Crawl شروع نمی‌شود؛ مگر اینکه فضای جست‌وجو واقعاً تمام شده باشد و batch ناقص باقی مانده باشد.
2. ثابت شود URLها دقیقاً یکی‌یکی پردازش می‌شوند.
3. بعد از تکمیل URL اول، Job در وضعیت انتظار باقی بماند و URL دوم شروع نشود.
4. ارسال `true` باعث شروع URL بعدی شود.
5. ارسال `false` باعث توقف شود و هیچ Crawl یا Search جدیدی اتفاق نیفتد.
6. حتی URL بدون شمارهٔ موبایل هم `url_completed` تولید کند.
7. خطای Firecrawl باعث حذف نتایج قبلی نشود و همچنان برای همان URL امکان تصمیم‌گیری وجود داشته باشد.
8. بعد از پایان ۱۰۰۰ URL اول، batch دوم از cursor قبلی جمع‌آوری شود.
9. هیچ URL تکراری در batch دوم یا batchهای بعدی وارد نشود.
10. جست‌وجو از محدودیت سه round عبور کند و به آن وابسته نباشد.
11. محدودیت ۵۰ صفحه باعث توقف اشتباه Search نشود.
12. ری‌استارت در حالت انتظار برای تصمیم، همان `decision_id` را حفظ کند.
13. تصمیم تکراری و تصمیم متناقض درست مدیریت شوند.
14. SSE با `Last-Event-ID` امکان بازیابی کامل رویدادهای از دست‌رفته را داشته باشد.
15. Job فقط پس از exhaustion واقعی تمام queryها و خالی شدن صف، `completed` شود.

`test_service.py` را هم تغییر بده؛ چون در معماری جدید باید رویدادهای SSE را به‌صورت زنده دریافت کند و برای هر `url_completed` یک Boolean ارسال کند. تست فعلی که ابتدا منتظر پایان Job می‌ماند و بعد SSE را می‌خواند، در این معماری باعث deadlock می‌شود.
